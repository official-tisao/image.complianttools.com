# P4-21 benchmark: T62 OCR

**Status:** The full pinned model catalogue, local Tesseract runtime, and lazy model delivery are registered. Browser smoke coverage includes eight generated language fixtures, one individually registered CC0 English paragraph, and the OSD, equation-adjunct, and deprecated-alias paths. These nine narrow OCR measurements do not establish quality across the expanded catalogue or real-world image classes.

## Pinned model catalogue

The catalogue is pinned to official `tessdata_fast` commit `87416418657359cb625c412a48b6e1d6d41c29bd`. The recursive upstream tree contains 163 `.traineddata` entries totaling 700,353,193 bytes:

| Entry type                          |   Count | Detail                                                                                                                                                  |
| ----------------------------------- | ------: | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Language and variant model binaries |     123 | Root language files, including legacy and vertical-text variants                                                                                        |
| Deprecated alias pointer            |       1 | `frk.traineddata` is a 20-byte upstream symlink pointer to `deu_latf.traineddata`; selecting `frk` resolves to `deu_latf` before Tesseract.js is called |
| Script model binaries               |      37 | Files under `script/`, requested with codes such as `script/Latin`                                                                                      |
| Helper model binaries               |       2 | `equ` and `osd`                                                                                                                                         |
| **Total**                           | **163** | **162 binary model files plus the alias pointer**                                                                                                       |

The catalogue assigns a readable label to every entry, keeps variants distinct, and separates `language`, `script`, and `helper` modes. The original required-language set remains English, French, Spanish, Hindi, Simplified Chinese, German, Japanese, and Italian. The pinned tree does not contain `hau.traineddata`; Hausa is not listed as available.

Example selection shapes:

```ts
{ language: 'eng' }
{ mode: 'script', script: 'script/Arabic' }
{ mode: 'helper', helper: 'osd' }
{ mode: 'helper', helper: 'equ', language: 'eng' }
```

`osd` calls Tesseract.js `worker.detect` with the required legacy core. `equ` is an equation model adjunct and is loaded with the selected language, such as `eng+equ`. Workers and core assets stay same-origin. For model data, the browser first checks the matching `/tessdata/` path; if every model needed by that worker is present, it uses those local files. Missing models normally use the exact jsDelivr URL pinned to this commit. The 89,384,811-byte `script/Latin.traineddata` is the exception: jsDelivr returns 403, so the selected Latin script model uses its exact pinned official raw GitHub source. The 29,252,466-byte `script/Cyrillic.traineddata` is the only bundled model because neither jsDelivr delivery nor an alternate remote path is relied on for it. Only the selected language, script, or helper model is requested. The test and benchmark preparers populate only their explicitly requested files into the ignored `apps/web/static/tessdata` cache, verifying each size and SHA-256; clean production builds prune that cache before static packaging. The registered upstream catalogue totals about 668 MiB, while a clean deployment includes the one 29.3 MB Cyrillic exception plus the 44,821,014 bytes of runtime/core assets. A user's image pixels remain in the browser.

Each model has a pinned raw URL, upstream tree blob id, GitHub-reported size, computed SHA-256, and Apache-2.0 register entry in [`docs/static-assets.json`](../../../../docs/static-assets.json). The `frk` row deliberately hashes the 20-byte upstream pointer, not a model binary. The corresponding catalogue entry marks it as a deprecated alias to `deu_latf`.

## Cyrillic-only cache browser test

The normal Playwright setup prepares the English and OSD files needed by the broader OCR suite. For a focused test of the one-file bundled cache, set `PLAYWRIGHT_SKIP_OCR_TESSDATA_PREFETCH=1` and filter to the Cyrillic test:

```powershell
$env:PLAYWRIGHT_SKIP_OCR_TESSDATA_PREFETCH = '1'
$env:PLAYWRIGHT_PORT = '4179'
pnpm exec playwright test e2e/ocr.spec.ts --project=chromium --grep "bundled Cyrillic"
```

On 2026-09-20, focused standard Playwright preview-server runs passed with only `apps/web/static/tessdata/script/Cyrillic.traineddata` present (29,252,466 bytes). The recognition test observed local `HEAD` and `GET` requests to `/tessdata/script/Cyrillic.traineddata`, no cross-origin requests, and successful script-mode recognition. A second browser test forced a 503 for the pinned English CDN model request and verified the model-download-specific recovery message. The separate page-load check verifies that no model data is requested until recognition is selected. An earlier full Chromium OCR suite passed with default English/OSD prefetch enabled (9/9 tests); that historical run prepared both models and pruned the ignored cache back to Cyrillic only.

After the catalogue-localization, keyboard-flow, and warmed-cache offline cases were added, the current 12-test Chromium OCR suite passed against a fresh Playwright production preview on 2026-09-20. It ran with `PLAYWRIGHT_SKIP_OCR_TESSDATA_PREFETCH=1` while the static cache contained only the same Cyrillic file. The run passed local Cyrillic script recognition, CDN fallback/error handling, English keyboard-only selection/recognition/download, all 124 language and 37 script catalogue checks (including Arabic and pseudo-locale labels), and repeated all eight measured-language recognitions offline in the same warmed page with identical output and zero external requests. The local server's `HEAD` 404s for absent language/helper files were the expected cache-miss probes before CDN delivery. This verifies first-use model fallback and same-page warmed reuse.

The static shell now registers a versioned same-origin service worker. On 2026-09-21, the bundled-Cyrillic test warmed the app, worker, core, and local model while controlled by that worker, then reloaded the page with browser networking offline and recognized again successfully in Chromium and Firefox. WebKit skips this fresh-page case because its browser-wide offline reload returns an internal error for this local File/Blob flow; the existing same-page WebKit coverage remains unchanged. Cross-origin CDN models are still not claimed as fresh-page offline: they require their browser-side Tesseract cache/IndexedDB entry and are subject to eviction, private browsing, and site-data clearing.

## Pinned catalogue reachability and Latin fallback

Run `pnpm ocr:verify-catalog` for a metadata-only source audit. It uses `HEAD` with identity encoding for all 162 lazy-CDN register rows, checks HTTP status, registered content length, pinned jsDelivr revision, CORS, and CORP, verifies the local Cyrillic file's registered size/hash, and checks the raw Latin source. It downloads no model payloads. On 2026-09-20, 161 jsDelivr rows passed; the Latin URL alone returned 403. Its raw GitHub URL returned 200 with the registered 89,384,811-byte length and the required CORS/CORP headers.

To exercise the actual on-demand worker path and check the full payload, run `pnpm ocr:cdn-smoke -- script/Latin`. The current implementation requested only the pinned raw Latin model, produced an OCR result for generated text, observed an HTTP 200 response with the registered content length and CORS/CORP headers, and independently streamed the exact pinned source to verify its 89,384,811-byte size and SHA-256 `6dbdaf8ecc6c40f025c2648bf3b3f3fbffe073e1fd2df2047fde2e2b2f020d53`. `pnpm ocr:fetch-assets -- script/Latin` also downloaded the named model into the ignored cache and passed its same size/hash check; that temporary cache file was removed after verification, leaving only Cyrillic in `apps/web/static/tessdata`. This is delivery/runtime evidence, not Latin OCR accuracy evidence.

## Generated language smoke measurements

The exact eight 1200×160 PNG inputs are persisted in [`../fixtures/ocr-language/`](../fixtures/ocr-language/) with their text, font stacks, dimensions, PNG hashes, decoded RGBA hashes, and renderer recipe in [`../fixtures/ocr-language/manifest.json`](../fixtures/ocr-language/manifest.json). The files total 115,246 bytes. Generate them with `node packages/engine/bench/generate-ocr-language-fixtures.mjs`; verify only the registered files and hashes with `node packages/engine/bench/generate-ocr-language-fixtures.mjs --verify`.

The repeatable runner is [`../ocr-language-smoke.mjs`](../ocr-language-smoke.mjs). It validates and decodes these saved PNGs, asserts the browser-decoded RGBA hash against the manifest, then requests only the eight fixture models, `osd`, `equ`, and `deu_latf` for the alias check. Missing local models are downloaded into the ignored cache only after size/hash verification. Detailed fixture text, output, input and PNG hashes, per-language errors and confidence, browser requests, helper results, and alias resolution are in [`../ocr-language-smoke-results.json`](../ocr-language-smoke-results.json). Run it from the repository root with `node packages/engine/bench/ocr-language-smoke.mjs`.

The optional external-delivery browser check is `pnpm ocr:cdn-smoke [script-model-id]`; it defaults to `script/Arabic` and supports `script/Latin` for the raw-source fallback. It runs a generated in-browser image through the selected script model with no matching static cache present and verifies the selected pinned source, response headers, size, and SHA-256 against the register. On 2026-09-20, Chromium 151 passed the Arabic jsDelivr check: it requested only the pinned model URL by GET, received 9,311,038 bytes with SHA-256 `47c262ac4e843c024df87ffa1363b77a821a843c069c71ef7650f4d2ecfea1e8`, and Tesseract returned an OCR result. The separate Latin result is recorded above. These checks verify model delivery and worker initialization, not OCR accuracy, and are not part of the offline test suite.

The eight language fixtures are self-generated black text on white PNGs; their saved RGBA hashes exactly match the original measured inputs. The updated Chromium 151 runner remeasured them through production Tesseract.js 7: 7/8 exact, mean CER `0.00735294`, no errors, and no page errors. It used hash-verified local model cache files and same-origin worker/core/data requests. These simple fixtures do not establish accuracy for the other language/variant, script, or helper models, or for handwriting, captures, skew, dense tables, or artistic fonts.

## Registered CC0 English print sample

[`fixtures/cc0/manifest.json`](fixtures/cc0/manifest.json) adds Wikimedia Commons' [Test OCR document](https://commons.wikimedia.org/wiki/File:Test_OCR_document.jpg) by Kaldari. Its file-level MediaWiki API snapshot records `LicenseShortName=CC0`, the CC0 1.0 deed, dimensions 2550×3300, and upstream SHA-1 `f00cba5fc4882a570170246d44febfdb746e22ac`. The checked-in JPEG is 583,690 bytes with SHA-256 `3b06e74ec9ddcdd647357cbda13ab264fa28ed1ce9a41ec16d116786f7b97f0b`; the metadata response is preserved and hash-verified.

The registered fixture takes the first English paragraph at native scale using crop `{ x: 270, y: 430, width: 1000, height: 540 }`. It excludes the adjacent French column. Run `node packages/engine/bench/escalation/t62/cc0-run.mjs` to verify the source and metadata, decode the crop in Chromium Canvas 2D, and send its pixels through the production OCR worker. The exact Chromium 151 input had RGBA SHA-256 `26074af79381a73cc7ab0cf2e6dbff719830e0af5d22052dbda2b68da25de96f`. The measured output changed `Alice` to `Aitice`; confidence was 94 and Unicode-codepoint CER was `0.00660066` (1/151). Full output, model requests, and measurement details are in [`t62/cc0-results.json`](t62/cc0-results.json).

This is one English paragraph from a deliberately typeset OCR test page. Together with the eight self-generated fixtures, it adds a third-party source with individually checked CC0 evidence, but it is not a representative accuracy estimate for scanned documents, photographs, handwriting, other languages, or the 163 registered models.

## Runtime and offline boundary

The registered OCR worker/core assets total 44,821,014 bytes before deployment compression, including 20,388,258 bytes of LSTM runtime files and 24,432,756 bytes of legacy core variants used by OSD. Worker and core assets are local and pinned separately from the data models.

An initial uncached OCR request requires the app, selected model, worker, and corresponding core to be available. The bundled Cyrillic path now has fresh-page offline evidence in Chromium and Firefox after service-worker warm-up. Other models remain CDN/IndexedDB dependent: the app shell and worker/core are service-worker cacheable, but model persistence after browser eviction, private browsing, or site-data clearing is not guaranteed.
